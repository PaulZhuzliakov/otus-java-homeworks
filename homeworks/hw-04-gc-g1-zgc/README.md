# hw-04-gc-g1-zgc

## шаг 1 - исходник как есть, куча 50m (gc-step1.log)

запускаю GcTest без изменений с размером кучи 50мб (размер кучи из комментария в GcTest) командой:

```
java -Xms50m -Xmx50m -XX:+UseG1GC -Xlog:gc*:file=gc-step1.log -cp target/classes com.otus.java.advanced.GcTest
```

падает с OutOfMemoryError. в логе gc-step1.log вижу, что последняя запись 0,134s и что было 13 Pause Full - от 47M->47M до 49M->49M(50M). т.е. упало примерно через 0,134s после запуска и видно что после отрабатывания сборщика, хип вообще не освобождается. либо куча мала, либо объекты вообще не подлежат очищению.

Проверяю на куче побольше - тем более в самом задании речь про 2 ГБ: меняю -Xms50m -Xmx50m на -Xms2g -Xmx2g, остальное без изменений

## шаг 3 - окно 2048 чанков, куча 2g (gc-step3.log)

нужно изменить код в main так, чтобы живыми оставались примерно 1 ГБ (половина кучи 2 ГБ - требование задания), а свыше 1 гб становилось мусором. сейчас код заполняет ArrayList 4096 раз по 512кб, то есть как раз 2 гб.

ArrayList al никогда не очищается. Нужно ограничить объём: когда чанков уже 2048 (это и есть 1 ГБ), при добавлении нового выбрасываем самый старый - перед add делаю remove(0)

выполняю

```
java -Xms2g -Xmx2g -XX:+UseG1GC -Xlog:gc*:file=gc-step3.log -cp target/classes com.otus.java.advanced.GcTest
```

снова падение с oom. анализирую лог gc-step3.log: время жизни до падения - 1,084s. всего 11 Pause Full почти все вида 2047M->2047M(2048M). получается у нас 1 гб объектов, но занимают 2гб памяти. смотрю на все записи Pause Full сборки по GC id - GC(21), тут есть разбивка по регионам:

```
[1,084s][info][gc,heap ] GC(21) Eden regions: 0->0(0)
[1,084s][info][gc,heap ] GC(21) Survivor regions: 0->0(0)
[1,084s][info][gc,heap ] GC(21) Old regions: 2->2
[1,084s][info][gc,heap ] GC(21) Humongous regions: 2046->2046
```

почти все Humongous regions - объекты размером более 50% региона отправляются в Humongous regions. размер региона 1Мб - `[0.109s][info][gc,init] Heap Region Size: 1M`. а чанки по 512 + заголовок объекта, т.е чуть больше половины региона и остаток региона пропадает впустую. надо уменьшить чанк или увеличить регион

## шаг 4 - окно 2048 чанков, регион 2m (gc-step4.log)

Из двух вариантов беру второй: увеличить регион флагом -XX:G1HeapRegionSize=2m. Половина региона станет 1M, наш чанк 512 KB с заголовком туда влезает - перестаёт быть humongous.

Код не меняю. Запуск:

```
java -Xms2g -Xmx2g -XX:+UseG1GC -XX:G1HeapRegionSize=2m -Xlog:gc*:file=gc-step4.log -cp target/classes com.otus.java.advanced.GcTest
```

не падает, я сам завершил процесс через 15 сек. в шапке Heap Region Size: 2M - флаг применился. 
Humongous regions: 0->0 - humongous больше нет. за весь прогон один Full GC: 2047M->1024M(2048M) - куча один раз дошла доверху, 
Full GC выкинул мусор, осталось 1024M - это и есть живое, ровно половина кучи, как просит задание

young-паузы по 10-30 ms, десятки раз в секунду, за 15 секунд прогона набежало секунд 10 стояния

флаг только для G1

## шаг 5 - окно 2048 чанков, ZGC (gc-step5.log)

меняю только сборщик на -XX:+UseZGC. флаг региона убираю - он только для G1, у ZGC нет регионов

выполняю

```
java -Xms2g -Xmx2g -XX:+UseZGC -Xlog:gc*:file=gc-step5.log -cp target/classes com.otus.java.advanced.GcTest
```

не упал, я сам завершил процесс через 22 секунды. в логе 355 сборок мусора - последняя GC(354), нумерация с нуля. паузы три на сборку (Mark Start, Mark End, Relocate Start), и они микросекундные: от 0,003 до 0,092 ms. суммарно около 18 ms за весь прогон - против 10 с пауз у G1 в шаге 4

189 раз main вставал в Allocation Stall (`[2,461s][info][gc] Allocation Stall (main) 3,224ms`) - место под новый чанк кончилось, и main ждёт, пока GC его освободит. в среднем 4,8 ms, суммарно 0,9 с. Full GC нет вообще

Live: 1032M (50%) - соответствует заданию. куда легли чанки: Medium Pages: 63 / 2016M - 63 страницы по 32M (в шапке лога: `Medium Page Size: 32M`), почти вся куча. на одну страницу влезает 64 чанка по 512 KB - пустот не образуется. поэтому для ZGC и не пришлось ничего подбирать: проблемы humongous из шага 3 тут нет как класса.

## разница и вывод

G1 убирает мусор эвакуацией живых объектов, и всё это во время stop-the-world пауз - поэтому паузы в миллисекундах. когда не успевает - Full GC. у меня: 571 young-пауза по 10-30 ms, суммарно 10 с стояния из 15,5 с прогона - две трети времени стоит

ZGC делает всё в фоне, параллельно с приложением. паузы - только точки синхронизации, микросекунды (на других кучах не проверял). цена - Allocation Stall (у меня 0,9 с из 21,8 с, 4%)

вывод: на этой нагрузке ZGC лучше. заблокировано 4% времени против 65% у G1. G1 имеет смысл где нужны ограниченные паузы в миллисекундах (цель MaxGCPauseMillis, дефолт 200 ms). здесь он проиграл
